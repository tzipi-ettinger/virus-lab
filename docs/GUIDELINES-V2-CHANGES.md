### 2.1 למה SQLite ולא משהו אחר

> 🔄 **הוחלף ב־18.10: המסד הוא PostgreSQL של Render.** הנימוקים כאן ובסעיף 3 נכתבו לפני שהוחלט על דומיין חי. בשרת חינמי אין דיסק קבוע, ולכן קובץ SQLite היה נמחק בכל הפעלה מחדש. ההחלטה, הסכמה והחיבור: [PLAN-DEV-B §2.4](PLAN-DEV-B.md). הנימוק "המידע לא יוצא מהמחשב" כבר לא נכון; הניסוח החדש על פרטיות הוא החלטה D12 שם.

לפני ההחלטה ביקשנו גם חוות דעת שנייה ובלתי תלויה, והיא הגיעה לאותה מסקנה.

- **השופטים יכולים להריץ את זה:** לא צריך להתקין כלום. קובץ ה-DB נוצר לבד כשהשרת עולה.
- **פרטיות:** המידע לא יוצא מהמחשב, בדיוק כמו בטיפ שבהנחיות. כדי למחוק את כל הנתונים מוחקים קובץ אחד שלא נכנס ל-Git.
- **3 ימים:** כל ה-SQL בקובץ אחד (`app/storage/repo.py`). אם המעבדה תעבור בעתיד ל-Postgres, מחליפים רק אותו.
- **ההנחיות ממליצות עליו בשמו.**

| חלופה | למה נפסלה |
|---|---|
| Supabase מאוחסן | שולח פרטי מטופלים לשירות חיצוני, בניגוד לטיפ הפרטיות. ההדגמה גם תלויה ברשת |
| Supabase בהתקנה עצמית | בערך 10 קונטיינרים בשביל 3 טבלאות |
| PostgreSQL (מקומי או Docker) | מחייב את השופטים להתקין Docker או Postgres על Windows, ולא נשתמש באף יכולת שלו |
| SQLModel / SQLAlchemy + Alembic | עלות הקמה ונעילת גרסאות מול FastAPI ו-Pydantic, בשביל 3 טבלאות ב-3 ימים |
| DuckDB | בנוי לאנליטיקה, חלש בהרבה כתיבות קטנות |
| קבצי JSON / TinyDB | אין טרנזקציות, ואת החיפוש והסינון היינו כותבות לבד |
| IndexedDB בדפדפן | הרשומות לא היו בשרת, אז ל-API העתידי של המעבדה אין מאיפה לקרוא |

> **הערה על "לא שומר יותר ממה שחייבים":** הכלל הזה עוסק ב**כמות** המידע, לא בסוג ה-DB. כל DB היה שומר אותו מידע בדיוק. אנחנו עונות עליו דרך D4.

## 3. שכבת השמירה (מפתחת B)

### 3.1 מבנה

```
backend/app/storage/
├── schema.sql   # CREATE TABLE IF NOT EXISTS ...
├── db.py        # connection per request, PRAGMAs, init on startup, user_version check
└── repo.py      # all SQL; takes and returns the Pydantic models from schemas/api.py
```

- קובץ ה-DB: `backend/data/virus-lab.db`, ונוסיף אותו ל-`.gitignore`. הנתיב מגיע ממשתנה הסביבה `DATABASE_PATH`.
- PRAGMAs: `journal_mode=WAL`, `busy_timeout=5000`, `foreign_keys=ON`.
- כל הטבלאות מוגדרות `STRICT`, וכל מזהה הוא `TEXT`, כדי שאפסים מובילים לא ייעלמו.
- כל עמוד נשמר עם כל הרשומות שלו **בטרנזקציה אחת**.

### 3.2 סכמה

```
page(id PK, source_filename, page_number INT, rotation INT, created_at)
page_image(page_id PK -> page ON DELETE CASCADE, mime, sha256, bytes BLOB)

record(id PK, page_id -> page, commitment_idx INT,
  status CHECK IN ('pending','approved'), needs_review INT, version INT,
  -- effective values (correction if present, else extracted), for search and filter:
  national_id, commitment_number, central_numbers,   -- ' 948062 123456 '
  first_name, last_name, sender, received_date,      -- ISO date
  search_text,                                       -- normalized Hebrew
  created_at, updated_at, approved_at)

record_field(record_id -> record ON DELETE CASCADE, field, idx INT DEFAULT 0,
  raw, value, model_status, evidence, issues_json,
  needs_review INT, corrected INT, confirmed INT, updated_at,
  PRIMARY KEY (record_id, field, idx))   -- idx = position for multiple central numbers
  -- matches SPEC v0.2 section 7.4: raw never changes, edits go to value + corrected

record_event(id PK, record_id, at, action, field, old, new)   -- audit log, optional if time is short

INDEX record(status, received_date), record(national_id), record(commitment_number)
```

### 3.3 תמונת העמוד

- נשמר **רק העמוד שממנו חולצו השדות**, אחרי סיבוב, כ-JPEG ברוחב של כ-1600px באיכות 80 (בערך 200–400KB).
- התמונה נשמרת כ-BLOB בתוך אותו קובץ DB. ככה אין קבצים יתומים, ומחיקה של עמוד מוחקת גם את התמונה שלו.
- היא מוגשת מ-`GET /api/v1/pages/{page_id}/image` עם `Cache-Control: no-store`.

### 3.4 שלוש נקודות שצריך לטפל בהן

1. **אפסים מובילים וחיפוש בעברית:** עמודות `TEXT` עם `STRICT`. `search_text` נבנה ב-Python: בלי ניקוד, עם איחוד של ״ ו-" ושל ׳ ו-', ובלי רווחים כפולים. מחפשים עם `LIKE '%…%'`. לא משתמשים ב-FTS5, כי הוא שובר חיפוש של חלק ממספר.
2. **שני חלונות שעורכים אותה רשומה:** עמודת `version`. השרת מריץ `UPDATE … WHERE version=?`, ואם אף שורה לא עודכנה הוא מחזיר `409`.
3. **שינוי סכמה:** `PRAGMA user_version`. אם הגרסה לא תואמת, השרת לא עולה ומציג הודעה ברורה ("למחוק את data/virus-lab.db"). בנוסף יהיה סקריפט seed שבונה מחדש את נתוני ההדגמה.

## 4. שינוי מוצע בחוזה (`schemas/api.py`, קובץ משותף, PR משותף)

המבנה של שדה בודד **לא משתנה** (SPEC v0.2 סעיף 9.2): `raw`, `value`, `model_status`, `evidence`, `issues`, `needs_review`, `corrected`, `confirmed`. גם הכללים של סעיף 7.4 נשארים כמו שהם (`raw` לא משתנה, עריכה מבטלת `confirmed`, והשרת לא סומך על `issues` / `needs_review` שמגיעים מהלקוח).

### 4.1 `Record` (במקום `form` כיחידת הפלט)

```json
{
  "record_id": "3f2a...-uuid",
  "page_id": "p_...",
  "source_file": "part1.pdf",
  "page_number": 25,
  "commitment_index": 0,
  "status": "pending",
  "version": 1,
  "fields": {
    "first_name":        { "raw": null, "value": null, "model_status": "unclear", "...": "same shape as today" },
    "last_name":         { "...": "..." },
    "national_id":       { "...": "..." },
    "received_date":     { "...": "..." },
    "sender":            { "...": "..." },
    "commitment_number": { "raw": "260005102632", "value": "260005102632", "...": "..." }
  },
  "central_numbers": [ { "raw": "948062", "value": "948062", "...": "..." } ],
  "issues": [],
  "needs_review": true,
  "created_at": "2026-10-18T10:00:00Z",
  "updated_at": "2026-10-18T10:00:00Z",
  "approved_at": null
}
```

- **`commitment_number` הוא שדה בודד ברשומה**, לא רשימה, כי כל רשומה מייצגת התחייבות אחת (D2).
- טופס **בלי** התחייבות הופך לרשומה אחת עם `commitment_number` ריק ומסומן לבדיקה (לפי SPEC 7.1). לפי D3 אי אפשר לאשר אותה עד שמשלימים את המספר.
- `preview_image` (base64) **יוצא מהתשובה**. התמונה נטענת מה-endpoint של העמוד (סעיף 3.3).

### 4.2 נקודות קצה

| Method | Path | מה עושה | בעלות |
|---|---|---|---|
| `GET` | `/api/health` | ללא שינוי | A |
| `POST` | `/api/v1/extract` | מריץ את הצינור כמו היום, **ובסוף שומר** את הרשומות בסטטוס `pending`. מחזיר `{ files, records, failed_pages }` | A (הקריאה לשמירה: B) |
| `GET` | `/api/v1/records` | רשימה. פרמטרים: `q` (חיפוש חופשי: שם, ת.ז., מרכזי, התחייבות), `status`, `sender`, `date_from`, `date_to`, `needs_review`, `limit`, `offset` | B |
| `GET` | `/api/v1/records/{id}` | רשומה מלאה | B |
| `PATCH` | `/api/v1/records/{id}` | תיקון או אישור של שדה. גוף הבקשה: `{ version, fields: { <name>: { value?, confirmed? } }, central_numbers?: [{ value, confirmed? }] }`. מריץ שוב את `apply_rules` לפי SPEC 7.4 ושומר. מחזיר `409` אם ה-`version` ישן | B |
| `POST` | `/api/v1/records/{id}/approve` | גוף הבקשה: `{ version }`. מריץ שוב את הכללים. אם נשאר שדה מסומן מחזיר `409` עם רשימת השדות, ואחרת `status=approved` | B |
| `GET` | `/api/v1/pages/{page_id}/image` | תמונת העמוד | B (משרת את `DocumentPreview` של A) |

**מה יוצא:**
- `POST /api/v1/validate` (SPEC v0.2 סעיף 9.3): `PATCH` עושה בדיוק אותו דבר (מריץ את הכללים אחרי תיקון או אישור), רק שהתוצאה נשמרת. אין צורך בשני endpoints.
- `POST /api/v1/export` (SPEC v0.2 סעיף 9.4).

## 8. שאלות ותשובות (שאלות שעשויות לעלות אצלך, עם התשובה שכבר הוחלטה)

**ש: למה לא Supabase? ההנחיות ממליצות עליו.**
ת: ההנחיות ממליצות על "SQLite / Supabase". Supabase המאוחסן שולח פרטי מטופלים לשירות חיצוני, וזה נוגד את טיפ הפרטיות באותו מסמך. SQLite עונה על הדרישה בלי לשלוח מידע החוצה. ראי סעיף 2.1.

**ש: למה לא Postgres? הוא "רציני" יותר.**
ת: הוא מחייב את השופטים להתקין Docker או Postgres. אנחנו לא צריכות אף יכולת שלו, וכל ה-SQL מרוכז בקובץ אחד, אז אפשר לעבור אליו בהמשך בלי לגעת בשאר הקוד.

**ש: האם הצינור שלי (פיצול, סיבוב, Gemini) משתנה?**
ת: **לא.** הצינור מחזיר את אותו מבנה כמו היום. בסוף נוסף שלב: בניית רשומות לפי מספרי ההתחייבות, ושמירה. השמירה עצמה (`repo.save_page`) אצלי, ואת צריכה רק לקרוא לה.

**ש: מה קורה לעמוד שהחילוץ שלו נכשל?**
ת: ההצעה היא **לא** לשמור אותו כרשומה. הוא מוחזר ב-`failed_pages` בתשובה של `extract` ומוצג במסך כנכשל, כמו היום (FR-12). ככה לא נשמר מידע שלא צריך.

**ש: האם `preview_image` נשאר בתשובה?**
ת: לא. התמונה נשמרת פעם אחת ב-DB ונטענת מ-`GET /api/v1/pages/{page_id}/image`. התשובה קטנה יותר, ואפשר לחזור לרשומה מחר ועדיין לראות את המקור.

**ש: למה רשומה לכל התחייבות ולא לכל טופס?**
ת: ככה כתוב בהנחיות ("רשומה לכל התחייבות"), וככה כל התחייבות מאושרת בנפרד. הכלל של SPEC 7.1 נשאר: 2 התחייבויות ו-3 מרכזיים נותנים **2 רשומות**, לא 6.

**ש: אז מה עם `/validate`?**
ת: נבלע ב-`PATCH /records/{id}`: אותה לוגיקה (מריצים שוב את הכללים), רק שהתוצאה נשמרת.

**ש: מה ההבדל בין `confirmed` לבין אישור רשומה?**
ת: `confirmed` הוא ברמת **שדה**: "בדקתי מול המקור, הערך נכון למרות האזהרה" (SPEC v0.2 סעיף 7.4). אישור רשומה (`status = approved`) הוא ברמת **הרשומה כולה**, ואפשר לעשות אותו רק כשאף שדה לא דורש בדיקה.

**ש: האם המודל קובע אם צריך בדיקה?**
ת: לא, כמו שכבר הוחלט ב-SPEC 8: `review_policy.py` קובע. עכשיו הוא גם מה שחוסם את האישור, בשרת.

**ש: מה עם מפתח ה-API ומה שנשלח ל-Gemini?**
ת: אין שינוי. הדבר היחיד שחדש הוא שמירה **מקומית**, ושום מידע נוסף לא יוצא החוצה.

**ש: מה עם `CachedProvider`?**
ת: אין שינוי. הוא נפרד מה-DB, ונשאר כבוי כברירת מחדל.
